# synthetic_demo: from nothing to a report in three commands

> **Synthetic data: for demos and CI only.** The `synthetic_v2` corpus is generated by a seeded
> program to have the same feature layout as EMBER2018. It contains no real files, and the model
> trained on it is not a real detector. **The verdict, the score and every number below say nothing
> about the real-world readiness of any detector.** Use the real-data examples for that.

You need only MalValid installed. No downloads. `--config gate.yaml` selects the `synthetic_v2` corpus (a model
file alone would default to the real `ember_v2_2018` corpus).

```bash
cd examples/synthetic_demo
python train.py                                                          # 1. train a demo model (4 s)
malvalid inspect-model model.txt                                         # 2. what malvalid detects (LightGBM, 2381 features -> ember_v2)
malvalid run --model model.txt --threshold 0.963108 --training-cutoff 2017-12-28 \
    --training-hashes train_sha256.txt --config gate.yaml --out runs/demo   # 3. verdict + report (10 s)
```

The model-file command gives exactly the same verdict and scores as the adapter route, which is the
alternative for custom pipelines:

```bash
malvalid validate-adapter --adapter adapter.py --config gate.yaml       # check the submission (5 s)
malvalid run --adapter adapter.py --config gate.yaml --out runs/demo    # verdict + report (10 s)
```

Then open `runs/demo/report.html` in a browser.

`train.py` (step 1) generates the `synthetic_v2` corpus on first use (about 3 s, cached under
`$MALVALID_CORPUS_DIR` or `~/.cache/malvalid/corpora`). The trained `model.txt`, `threshold.txt` and
`train_sha256.txt` also ship in this folder (they are what the web UI's **Run the synthetic demo** button
evaluates), so you can skip step 1; any command that needs the corpus generates it.

## What each file does

* `train.py` trains a LightGBM on the corpus's `train` split (5,315 labeled rows from 2017). It picks
  the operating threshold for 1% FPR on the separate `holdout` split (the same 2017 months, rows
  the model never saw), never on the `test` split that M1 scores. It writes:
  * `model.txt`: LightGBM text format, a safe non-pickle format that M0 can scan;
  * `threshold.txt`: the threshold (0.963108);
  * `train_sha256.txt`: the sha256 of every `train` row, the training members for M4.

  It ends by printing the `training_cutoff` (newest `train` row, `2017-12-28`) that `adapter.py`
  declares. If you change the corpus size or seed, copy the new value into `adapter.py`. Training is
  deterministic.
* `adapter.py` is the alternative to the `--model` flags above. It declares `feature_version = "ember_v2"`, `model_kind = "lightgbm"`, the threshold read
  from `threshold.txt`, `model_path = "model.txt"`, `training_hashes_path = "train_sha256.txt"` and
  the cutoff. See [../README.md](../README.md#what-an-adapter-declares) for what each one means.
* `gate.yaml` is based on the default policy from `malvalid init-config`, with `corpus: synthetic_v2`.
  Settings it leaves out take their defaults.
  Thresholds, hard/warn gates and verdict weights are all policy you can change.

## What you should see

All modules run (M0, M1, M2, M4, M5, M7; M6 is off by default), so coverage is 100%. Measured on
a cluster node, run time 9.6 s:

| Module | Status | Score | Evidence |
|---|---|---|---|
| M0 file safety | pass | (precondition) | no unsafe content in `model.txt` |
| M1 performance | **fail** (hard gate) | 0.0 | FPR 1.21% (max 1.00%), detection 69.4% (min 95.0%) at threshold 0.9631 |
| M2 drift | **warn** | 88.5 | AUT(F1) 0.808 over 24 monthly windows passes (min 0.70); F1 falls from 0.940 to 0.712. The worst window's FPR (2.3%, 2018-12-28..2019-01-27; 95% lower bound 1.07%) exceeds the 1% budget. That check is ungraded: it fails the warn gate but does not change the score |
| M4 membership inference | warn | 27.1 | advantage 0.228 (limit 0.10) |
| M5 backdoor screening | pass | 100.0 | no backdoor-like rules in 200 trees |
| M7 explanation | pass | 78.8 | 44.7% of attribution on attacker-controllable features (limit 50%) |

Verdict: **BLOCKED, score 45.2/100** (already below the BLOCKED cap of 49). Exit code 1.

This is the intended demo outcome, and it shows how the gate reads a result. The synthetic world
introduces new malware families after the training months, as real threat landscapes do. The 1% FPR
threshold was tuned on 2017 data, so on the 2018-2019 test months detection drops to 69% and the
hard M1 gate blocks the model. The M1 finding also says which threshold would meet the FPR limit on
the gate's data (0.9741, at 66.2% detection). Do not adopt it: retrain or pick a threshold on your
own held-out data. M2 shows the mechanism (F1 decays month by month, and in one window the frozen
threshold's FPR is well over budget), and M4 flags leakage of training membership.

To see a different outcome, relax the M1 policy in a copy of `gate.yaml` (`modules.performance.max_fpr:
0.02` and `min_detection: 0.6`) and re-run: the hard gate passes and the verdict becomes CONDITIONAL,
score 77.3 (measured). Relaxing the policy to get a better verdict is exactly what you should not do
with a real detector; this only shows that thresholds are policy, not physics.
